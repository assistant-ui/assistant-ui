A runtime is the conversation's state and the engine that moves it forward. It keeps the messages, the text in the composer, the reply in progress and every earlier version of an edited message. When the user sends, the runtime calls your backend and turns the answer into a message as it streams in.

Components never call your backend. They read state from the runtime and send it actions such as send, edit, regenerate and cancel. That split is why you can restyle the whole chat without touching how it talks to the model, or swap the backend without touching a component.

## One runtime per chat

You create a runtime with a hook and hand it to `AssistantRuntimeProvider`. Every component inside the provider reads from that runtime.

The smallest runtime is `useLocalRuntime`. You give it one function that calls your API with the thread's messages and returns the reply:

```tsx title="app/MyRuntimeProvider.tsx"
"use client";

import type { ReactNode } from "react";
import {
  AssistantRuntimeProvider,
  useLocalRuntime,
  type ChatModelAdapter,
} from "@assistant-ui/react";

const MyModelAdapter: ChatModelAdapter = {
  async run({ messages, abortSignal }) {
    const result = await fetch("<YOUR_API_ENDPOINT>", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ messages }),
      signal: abortSignal,
    });
    const data = await result.json();
    return {
      content: [{ type: "text", text: data.text }],
    };
  },
};

export function MyRuntimeProvider({
  children,
}: Readonly<{ children: ReactNode }>) {
  const runtime = useLocalRuntime(MyModelAdapter);
  return (
    <AssistantRuntimeProvider runtime={runtime}>
      {children}
    </AssistantRuntimeProvider>
  );
}
```

Most apps use a runtime made for their backend instead, such as `useChatRuntime` for the Vercel AI SDK or `useLangGraphRuntime` for LangGraph. They all expose the same state to the components, so the rest of your app doesn't change when you switch. [Picking a runtime](/docs/runtimes/pick-a-runtime) lists them.

## A turn, step by step

1. The user sends from the composer. The runtime adds their [message](/docs/concepts/messages) to the thread and clears the composer.
2. The runtime starts a run. It adds an empty assistant message with the status `running` and sends your backend the messages so far, along with the system instructions and tools your app has registered.
3. Your backend streams its answer. The runtime turns each piece into a part of the assistant message: text, reasoning, a tool call. Components re-render as the parts grow.
4. The run ends. The status becomes `complete`, `incomplete` with a reason such as `cancelled` or `error`, or `requires-action` when a tool call is waiting for a result or for the user.

With `ExternalStoreRuntime`, and the framework runtimes built on it, your store or the framework does the adding and streaming, and the runtime renders the messages the store holds. The turn looks the same on screen.

Editing a message or regenerating a reply starts a new run from that point. The earlier reply is kept as a branch, so the user can switch back to it.

Your components see this through state. A stop button, for example, reads whether a run is in progress and calls `cancelRun`:

```tsx
import { useAui, useAuiState } from "@assistant-ui/react";

function StopButton() {
  const aui = useAui();
  const isRunning = useAuiState((s) => s.thread.isRunning);
  if (!isRunning) return null;
  return <button onClick={() => aui.thread.cancelRun()}>Stop</button>;
}
```

[The Context API](/docs/concepts/context-api) covers every scope you can read this way.

## What the runtime owns, and what you own

| The runtime owns | You own |
| --- | --- |
| The messages of the open thread, their parts and status | The backend that calls the model, and its API keys |
| The composer's text and attachments | Server-side tools and what they can reach |
| The run in progress, and cancelling it | Where threads are stored, through an [adapter](/docs/concepts/adapters) or [Assistant Cloud](/docs/cloud) |
| Branches from edits and regenerations | The components, which you can restyle or replace |
| The thread list, once you give it somewhere to keep [threads](/docs/concepts/threads) | |

## Two cores: the runtime keeps the messages, or you do

Every runtime is built on one of two core runtimes. Which one sits under yours decides who holds the messages.

`LocalRuntime` keeps the messages itself. You write the call to your backend, as in the example above, and editing, regenerating and branching work without more code.

`ExternalStoreRuntime` reads the messages from a store you already have, such as Redux or Zustand, and calls your handlers when the user sends, edits or regenerates. Features turn on as you provide the handlers for them.

| | LocalRuntime | ExternalStoreRuntime |
| --- | --- | --- |
| Who holds the messages | The runtime | Your store |
| Setup | One `run` function | Messages plus a handler per action |
| Editing and branching | Built in | Turned on by `onEdit` and `setMessages` |
| Best fit | A new app with its own API | An app whose state already lives in a store |

The runtimes for frameworks build on these. `useChatRuntime`, `useLangGraphRuntime` and the other framework runtimes sit on `ExternalStoreRuntime`, because the framework already keeps the messages. Two wire protocols sit in between for backends you write yourself: the [data stream](/docs/runtimes/custom/data-stream) protocol streams message parts on top of `LocalRuntime`, and [assistant transport](/docs/runtimes/custom/assistant-transport) streams your agent's whole state on top of `ExternalStoreRuntime`.

Start at the top and go down a layer only when the one above can't do what you need. Features such as attachments, speech and feedback plug in through [adapters](/docs/concepts/adapters), which work the same way in every runtime that supports them; the adapters page lists which runtime supports which.
