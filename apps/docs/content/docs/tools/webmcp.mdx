title: WebMCP provider
description: "Expose your app's frontend tools to a WebMCP-capable browser with unstable_useWebMcpProvider."
---

WebMCP is a browser-native way for a page to publish tools to the agent the *user* is running, through `document.modelContext` (with `navigator.modelContext` as a fallback). A page calls `registerTool` and the agent can call it. It runs the opposite way from the other [MCP pages](/docs/tools/mcp#which-mcp-page-do-i-need): your page is the tool server, not an MCP client.

By default the explainer exposes a registered tool to the page itself, to same-origin documents in the same frame tree, and to the browser's built-in agent. Reaching an author-provided agent in another origin needs the `exposedTo` option, which this hook does not set, so treat the audience as the built-in agent unless that changes.

`unstable_useWebMcpProvider` connects the two directions you already have. Every frontend tool registered in the assistant-ui model context is published to the browser's WebMCP host, and calls run through the same `Tool` contract your chat runtime uses. You define a tool once, and both your assistant and the user's browser agent can call it.

<Callout type="warn">
  This hook is `unstable_`. WebMCP itself is an emerging browser API and the
  shape of this hook will change with it. It is exempt from the usual
  append-only surface guarantee.
</Callout>

## Browser support

Chrome exposes `document.modelContext` behind the `chrome://flags/#enable-webmcp-testing` flag. Enable it and relaunch Chrome to turn the API on for every origin, including `localhost`. The [WebMCP origin trial](https://developer.chrome.com/origintrials/#/view_trial/4163014905550602241) covers Chrome 149 to 156 only, so from Chrome 157 a deployed site cannot turn the API on for its visitors. On Chrome 157 and later without the flag, Chrome provides no `modelContext`, so `status` is `"unsupported"` unless an extension injects one.

Chrome's [WebMCP guide](https://developer.chrome.com/docs/ai/webmcp) covers the API and links to the trial's current status.

## Usage

Mount it once, anywhere under the provider that registers your tools:

```tsx title="app/page.tsx"
import { unstable_useWebMcpProvider } from "@assistant-ui/react";

const WebMcpTools = () => {
  const { status, registeredToolNames } = unstable_useWebMcpProvider();

  if (status === "unsupported") return null;
  return <span>Exposed to your browser: {registeredToolNames.join(", ")}</span>;
};
```

`status` is `"unsupported"` when the page has no `modelContext` (see [Browser support](#browser-support)) and `"active"` once the provider is running. The check runs when the hook mounts and is not repeated: WebMCP defines no availability event, and the provider does not poll, so an extension that injects `modelContext` into an already-rendered page is only picked up on the next mount.

`registeredToolNames` is the sorted list of names the provider is publishing. A name the host refuses (because the page already registered it, or because the page's tools permission is off) drops out once the refusal arrives. A name appears in the commit that sets up its registration, so read the list as what the provider intends to have live, not a synchronous read of the host.

With no `filter`, the provider publishes every enabled frontend tool that has an `execute`. Backend tools, disabled tools, and tools with no client-side implementation are skipped, and so are `type: "mcp"` toolkit entries, which never reach the model context. A tool authored without a `type` counts as frontend when it has an `execute`. A `filter` you pass **replaces** that default; see below.

A complete setup, a task-list page whose toolkit is published to the browser with one destructive tool held back, runs in [`examples/with-webmcp`](https://github.com/assistant-ui/assistant-ui/tree/main/examples/with-webmcp).

## Choosing which tools to publish

Pass a `filter` to choose which tools to publish. It runs for every tool on every model-context change, and changing the function re-syncs the registrations. An inline arrow is fine: each tool's converted schema is cached against the tool object, so a re-sync that changes nothing costs no schema conversion for toolkit tools. Tools added through `ModelContextRegistry.addTool` are rebuilt on every read, so they miss that cache. The re-sync still registers nothing new, it only re-converts.

Your `filter` **replaces** the default predicate. It does not run after it, so a name-only filter such as `PUBLIC_TOOLS.has(name)` publishes a backend or disabled tool whose name is in the set. To narrow the default instead, compose against the exported predicate:

```tsx
import {
  unstable_useWebMcpProvider,
  unstable_defaultWebMcpFilter,
} from "@assistant-ui/react";

const PUBLIC_TOOLS = new Set(["search_docs", "get_order_status"]);

unstable_useWebMcpProvider({
  filter: (name, tool) =>
    unstable_defaultWebMcpFilter(name, tool) && PUBLIC_TOOLS.has(name),
});
```

Replacement is deliberate. It is also the only way to widen the set, by publishing a tool the default would skip.

## Security

A tool the browser agent can call is a tool *anyone* driving that browser can call, without your assistant's system prompt or approval step in the loop. Publish only what you would expose as an unauthenticated API for the current session, and keep destructive tools out. Allowlist by name, as above, so a tool added to the toolkit later is not published by accident.

- **`human()` is unavailable.** A call from WebMCP rejects with `human input not supported in WebMCP context`, which the agent receives as an error result. A tool that asks for approval through `human()` therefore cannot be approved there. It fails, while a tool that never asks runs unasked.
- **User-managed MCP tools are frontend tools.** Tools from [user-managed MCP servers](/docs/tools/user-managed-mcp) have an `execute`, so the default filter publishes them. Exclude them unless you want the browser agent to use the user's connected servers; a server with `requireApproval: false` would run without any prompt.
- **Tool results are page data.** What your tool returns goes to whichever agent called it.

## Lifecycle

The provider owns its registrations:

- A tool that leaves the model context is unregistered.
- Changing a tool's `description`, or replacing the tool object with a different `parameters` schema, re-registers it under the new signature. Changing only its `execute` does not, because the live registration calls through to the latest version. Editing the schema inside the same tool object is not observed, since detecting that would cost a schema conversion for every tool on every change.
- Unmounting unregisters everything.
- A registration the host rejects is dropped with a `console.warn`, and its name is left alone, since the provider only aborts its own registration signal. The name is not retried while the tool stays in the model context, so a permanent collision warns once. A *transient* collision is not retried either: if the page later frees the name, the provider does not notice. Remove the tool from the model context and add it back, or remount, to retry.

A call runs through the same path as a frontend tool call. Standard Schema parameters are validated first (including `experimental_onSchemaValidationError`), `toModelOutput` shapes the result when you define it, and the host's `AbortSignal` is merged with the registration's own lifetime, so an unregistered tool cancels in-flight work.

## Troubleshooting

| Symptom or message | Cause and fix |
| --- | --- |
| `status` stays `"unsupported"` | The page has no `document.modelContext`. See [Browser support](#browser-support). The check runs once on mount, so reload after enabling the flag. |
| `[assistant-ui] WebMCP registration for tool "x" was not permitted; the page's tools permission is disabled.` | The page's tools permission is off, which a cross-origin iframe without `allow="tools"` hits. Grant it, or mount the hook in the top-level page. |
| `[assistant-ui] WebMCP registration for tool "x" failed (name may already be registered).` | The page or another script already registered that name. Rename the tool or unregister the other one. |
| `[assistant-ui] Skipping WebMCP registration for tool "x": filter or schema conversion failed.` | Your `filter` or the tool's `parameters` threw. The error follows the message. |
| A tool is missing from `registeredToolNames` | It is a backend, human, disabled, or `execute`-less tool, your `filter` excluded it, or the host refused it. |
| The agent gets `human input not supported in WebMCP context` | The tool calls `human()`. See [Security](#security). |
| The agent gets `Tool "x" has no client-side implementation.`, `Tool "x" is no longer registered`, or `Tool execution was cancelled.` | The tool has no `execute`, the call arrived after the tool was unregistered, or the call was aborted. |

## API

```ts
type Unstable_WebMcpProviderOptions = {
  filter?: (name: string, tool: Tool<any, any>) => boolean;
};

type Unstable_WebMcpProviderResult = {
  status: "unsupported" | "active";
  registeredToolNames: readonly string[];
};
```
