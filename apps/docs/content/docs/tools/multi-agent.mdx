In a multi-agent (orchestrator) architecture, a main agent invokes sub-agents via tool calls. Each sub-agent may produce its own conversation (user/assistant messages, tool calls, etc.). assistant-ui supports rendering these nested conversations using the `MessagePartPrimitive.Messages` primitive.

## Overview

When a tool call includes a `messages` field (`ToolCallMessagePart.messages`), it represents a sub-agent's conversation history. `MessagePartPrimitive.Messages` reads this field from the current tool call part and renders it as a nested thread.

Key behaviors:

- **Scope inheritance** — Parent toolkit renderers are available in sub-agent messages. A `Tools({ toolkit })` registration at the top level works inside sub-agent conversations too.
- **Recursive** — Sub-agent messages can contain tool calls that themselves have nested messages. Just use `MessagePartPrimitive.Messages` again.
- **Read-only** — Sub-agent messages are rendered in a readonly context. No editing, branching, or composing.

<Callout type="info">
  This renders a sub-agent's **messages**. To visualize a sub-agent's **execution trace** instead (timing, span hierarchy, waterfalls), see [react-o11y](/docs/utilities/react-o11y), which renders observability spans as collapsible trees and timelines.
</Callout>

import {

const toolkit = defineToolkit({
  invoke_researcher: {
    type: "backend",
    render: ({ args, status }) => (
    <div className="my-2 rounded-lg border p-4">
      <div className="mb-2 text-sm font-medium text-gray-500">
        Researcher Agent {status.type === "running" && "(working...)"}
      </div>
      <MessagePartPrimitive.Messages>
        {({ message }) => {
          if (message.role === "user") return <MyUserMessage />;
          return <MyAssistantMessage />;
        }}
      </MessagePartPrimitive.Messages>
    </div>
  ),
  },
});

### Provide the Messages from the Backend

The sub-agent's conversation has to reach `ToolCallMessagePart.messages`. An AI SDK backend populates it from the tool result. The LangGraph runtime assembles it from subgraph events, the AG-UI runtime from the protocol's subagent lifecycle events, the LangChain runtime from the subagent discovered for each `task` tool call, and the OpenCode runtime from the child session behind each `task` tool call. Google ADK leaves it unset: a long-running call there is owned by the client and settles on `requires-action` until the function response is sent, see [long-running tools](/docs/runtimes/google-adk/hooks#long-running-tools).

tools: {
  invoke_researcher: tool({
    description: "Invoke the researcher sub-agent",
    inputSchema: z.object({ query: z.string() }),
    execute: async ({ query }) => {
      const subAgentMessages = await runResearcherAgent(query);
      return {

        messages: subAgentMessages,

<Tab value="LangGraph">

With `@assistant-ui/react-langgraph`, use `unstable_createLangGraphStream` and set `unstable_allowCancellation: true` to wire up the stop button. When your graph runs a subgraph, the subgraph's messages appear on `ToolCallMessagePart.messages` automatically once you handle the `onSubgraphValues` / `onSubgraphUpdates` events.

```ts title="runtime.ts"
import {
  useLangGraphRuntime,
  unstable_createLangGraphStream,
} from "@assistant-ui/react-langgraph";

const runtime = useLangGraphRuntime({
  unstable_allowCancellation: true,
  stream: unstable_createLangGraphStream({
    client,
    assistantId,
    // "custom" is required for generative UI; "updates" for subgraph events
    streamMode: ["messages", "updates", "custom"],
    // abort the run server-side when the user clicks stop
    onDisconnect: "cancel",
  }),
  eventHandlers: {
    onSubgraphValues: (namespace, values) => {
      // namespace = e.g. "tools:call_abc" — the sub-agent's node path
      // values contains the subgraph state, including its messages array
    },
    onSubgraphUpdates: (namespace, updates) => {
      // incremental state updates from the subgraph
    },
    onSubgraphError: (namespace, error) => {
      // error scoped to the subgraph; does not mark the parent message failed
    },
    onMessageChunk: (chunk, metadata) => {
      // metadata.namespace is set when the chunk originates from a subgraph
      // use it to attribute the chunk to the correct sub-agent
    },
  },
});
```

See [LangGraph Streaming](/docs/runtimes/langgraph/streaming) for the full event handler reference.

</Tab>
<Tab value="AG-UI">

With `@assistant-ui/react-ag-ui` there is no `messages` field to populate: the runtime builds the nesting from the protocol's own subagent lifecycle. A backend running the agents-as-tools pattern emits `SUBAGENT_STARTED` naming the spawning call as `parentToolCallId`, tags every event that subagent produces with its `subagentRunId`, and closes the run with `SUBAGENT_FINISHED` or `SUBAGENT_ERROR`. The runtime groups each run into one nested assistant message and attaches it to that call's `ToolCallMessagePart.messages`, so the tool UI above renders it unchanged.

The subagent's `name`, `description`, `result`, `interruptIds`, and `errorCode` ride on the nested message's `metadata.custom.agui`. A run whose `parentToolCallId` names no reachable call has nowhere to nest and renders in the parent thread instead.

See [AG-UI Subagents](/docs/runtimes/ag-ui/runtime-options#subagents) for the full behavior, the comparison with LangChain's discovery-hook shape, and two limitations (nesting does not survive a reload, and nested human-in-the-loop has no resume path).

## Subgraph Namespace Events

When using LangGraph, subgraph events (`onSubgraphValues` / `onSubgraphUpdates` / `onSubgraphError`, plus the `namespace` on `onMessageChunk`) carry a `namespace` that identifies which sub-agent emitted them, letting you attribute messages and state to specific sub-agents. See [LangGraph Streaming](/docs/runtimes/langgraph/streaming) for the full reference.

## Recursive Sub-Agents

If a sub-agent's tool calls also have nested messages, the same pattern applies recursively:

```tsx
const toolkit = defineToolkit({
  invoke_planner: {
    type: "backend",
    render: () => (
    <div className="rounded border p-3">
      <h4>Planner Agent</h4>
      <MessagePartPrimitive.Messages>
        {({ message }) => {
          if (message.role === "user") return <MyUserMessage />;
          return (
            <MessagePrimitive.Parts>
              {({ part }) => {
                if (part.type === "text") return <MyText />;
                if (part.type === "tool-call" && part.toolName === "invoke_researcher") return (
                  <div className="ml-4 rounded border p-3">
                    <h5>Researcher Agent</h5>
                    {/* Nested sub-agent renders recursively */}
                    <MessagePartPrimitive.Messages>
                      {({ message }) => {
                        if (message.role === "user") return <MyUserMessage />;
                        return <MyAssistantMessage />;
                      }}
                    </MessagePartPrimitive.Messages>
                  </div>
                );
                if (part.type === "tool-call") return <MyToolFallback {...part} />;
                return null;
              }}
            </MessagePrimitive.Parts>
          );
        }}
      </MessagePartPrimitive.Messages>
    </div>
  ),
  },
});
```

## Status

While a nested conversation has a running assistant message, the tool call and the message that holds it stay `running` even after the outer run has ended. This is how delegated work that outlives the run shows up. Once the nested conversation settles without a tool result, the message reads `requires-action` with reason `tool-calls`, the same as any other pending tool call.

The nested thread rendered by `MessagePartPrimitive.Messages` or `ReadonlyThreadProvider` reports `isRunning` from its trailing assistant message, and the background rule reads the same trailing message. A runtime that fills `messages` owns settling the nested status: a trailing nested assistant message left `running` keeps the outer message `running` until it is settled. On the `useExternalMessageConverter` path a cancelled run clears it; on the plain `useExternalStoreRuntime` path the store settles the nested transcript on cancel as well. A transcript imported from persistence starts idle: a nested message that was saved while running does not keep the outer message running.

## Tasks

`s.thread.tasks` derives child work from every tool call that carries a `messages` array, including an empty array. Tasks follow document order, with nested tasks directly after their parent. Each task includes `parentTaskId` and `depth` for reconstructing the hierarchy.

The array keeps its identity while no task changes, so a component that subscribes to it does not rerender for unrelated streamed tokens. The walk stops past 32 levels of nesting; deeper tasks are not listed.

```tsx
import { useMemo } from "react";
import { useAuiState } from "@assistant-ui/react";

function TasksChip() {
  const tasks = useAuiState((s) => s.thread.tasks);
  const { running, total } = useMemo(
    () => ({
      running: tasks.filter((task) => task.status.type === "running").length,
      total: tasks.length,
    }),
    [tasks],
  );

  return <span>{`${running}/${total} tasks running`}</span>;
}
```

For imperative lookup, `aui.thread.task({ id })` resolves the first task with that toolCallId in document order (nested conversations may repeat ids), or use an index selector.

## ReadonlyThreadProvider

For advanced use cases where you have a `ThreadMessage[]` array and want to render it as a thread outside of a tool call context, use `ReadonlyThreadProvider` directly:

```tsx
import {
  ReadonlyThreadProvider,
  ThreadPrimitive,
  type ThreadMessage,
} from "@assistant-ui/react";

function SubConversation({
  messages,
}: {
  messages: readonly ThreadMessage[];
}) {
  return (
    <ReadonlyThreadProvider messages={messages}>
      <ThreadPrimitive.Messages>
        {({ message }) => {
          if (message.role === "user") return <MyUserMessage />;
          return <MyAssistantMessage />;
        }}
      </ThreadPrimitive.Messages>
    </ReadonlyThreadProvider>
  );
}
```

`ReadonlyThreadProvider` inherits the parent's tool UI registrations and model context through scope inheritance.
