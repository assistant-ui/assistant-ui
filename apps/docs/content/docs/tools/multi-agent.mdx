In a multi-agent (orchestrator) architecture, a main agent invokes sub-agents via tool calls. Each sub-agent may produce its own conversation (user/assistant messages, tool calls, etc.). assistant-ui supports rendering these nested conversations using the `MessagePartPrimitive.Messages` primitive.

## Overview

When a tool call includes a `messages` field (`ToolCallMessagePart.messages`), it represents a sub-agent's conversation history. `MessagePartPrimitive.Messages` reads this field from the current tool call part and renders it as a nested thread.

Key behaviors:

- **Scope inheritance**: Parent toolkit renderers are available in sub-agent messages. A `Tools({ toolkit })` registration at the top level works inside sub-agent conversations too.
- **Recursive**: Sub-agent messages can contain tool calls that themselves have nested messages. Use `MessagePartPrimitive.Messages` again to render them.
- **Read-only**: Sub-agent messages are rendered in a readonly context, without editing, branching, composing, or answering tool calls. A tool UI inside it reads `s.thread.capabilities.answerToolCall` as `false` and should [show the request without its controls](/docs/tools/tool-ui#human-in-the-loop).

<Callout type="info">
  This renders a sub-agent's **messages**. To visualize a sub-agent's **execution trace** instead (timing, span hierarchy, waterfalls), see [react-o11y](/docs/utilities/react-o11y), which renders observability spans as collapsible trees and timelines.
</Callout>

## Quick Start

<Steps>

### Register a Tool UI for the Sub-Agent

`MyUserMessage` and `MyAssistantMessage` are your own message components. Inside the nested thread, `MessagePrimitive.Parts` and the other message and part primitives work as they do in the main thread.

```tsx title="app/sub-agent-toolkit.tsx"
"use client";

import { defineToolkit, MessagePartPrimitive } from "@assistant-ui/react";

export default defineToolkit({
  invoke_researcher: {
    type: "backend",
    render: ({ status }) => (
      <div className="my-2 rounded-lg border p-4">
        <div className="mb-2 text-sm font-medium text-muted-foreground">
          Researcher agent {status.type === "running" && "(working)"}
        </div>
        <MessagePartPrimitive.Messages>
          {({ message }) =>
            message.role === "user" ? <MyUserMessage /> : <MyAssistantMessage />
          }
        </MessagePartPrimitive.Messages>
      </div>
    ),
  },
});
```

The sub-agent tool is defined on your backend, so this entry only attaches a renderer to it. In a plain `"use client"` toolkit that is `type: "backend"` with a `render`. In a `"use generative"` file write `execute: externalTool()` instead; see [Externally defined tools](/docs/tools/defining-tools#externally-defined-tools).

  </Step>

### Provide the Messages from the Backend

The sub-agent's conversation has to reach `ToolCallMessagePart.messages`. Whether it does depends on the runtime:

| Runtime | `messages` comes from |
| --- | --- |
| AG-UI | The protocol's subagent lifecycle events (see the AG-UI tab) |
| LangChain | The subagent discovered for each `task` tool call |
| OpenCode | The child session behind each `task` tool call |
| `useExternalStoreRuntime` | Your `convertMessage`: a tool-call part or a `role: "tool"` message carries `messages` (see the External store tab) |
| Backends on `assistant-stream` (data stream, assistant transport) | The `messages` field of the tool result, for example `new ToolResponse({ result, messages })`. The runtime copies it onto the part unchanged, so it has to be `ThreadMessage` shaped |
| LangGraph | Not set. Subgraph messages stream into the parent thread (see the LangGraph tab) |
| Google ADK | Not set. A long-running call is owned by the client and settles on `requires-action` until the function response is sent; see [long-running tools](/docs/runtimes/google-adk/hooks#long-running-tools) |
| AI SDK (`useChatRuntime`) | Not set. A tool output that contains a `messages` array stays on the call's `result`, so render it from there or move the sub-agent to a runtime above |

<Tabs items={["External store", "LangGraph", "LangChain", "AG-UI"]}>
<Tab value="External store">

With `useExternalStoreRuntime`, the tool-call part your `convertMessage` returns can carry the nested transcript. `messages` takes full `ThreadMessage` objects:

```ts title="convertMessage.ts"
import type { ThreadMessageLike } from "@assistant-ui/react";

const convertMessage = (message: MyMessage): ThreadMessageLike => ({
  id: message.id,
  role: message.role,
  content: message.parts.map((part) =>
    part.kind === "researcher"
      ? {
          type: "tool-call",
          toolCallId: part.id,
          toolName: "invoke_researcher",
          args: part.args,
          result: part.answer,
          messages: part.transcript,
        }
      : { type: "text", text: part.text },
  ),
});
```

A converter that returns separate `role: "tool"` messages can set `messages` there instead. A tool result that omits it keeps the `messages` the call already had. See [Status](#status) for who settles a nested transcript that is still running.

</Tab>
<Tab value="LangGraph">

`@assistant-ui/react-langgraph` does not nest subgraph output. Messages a subgraph emits stream into the parent thread, and the namespaced events attribute them: `onSubgraphValues` and `onSubgraphUpdates` receive the subgraph's namespace and state, `onSubgraphError` receives errors scoped to the subgraph, and `onMessageChunk` carries `metadata.namespace` for chunks that originate in a subgraph. Those events exist only when the run streams subgraphs, so `unstable_createLangGraphStream` forwards `streamSubgraphs` to `client.runs.stream` and this example enables it together with `"updates"` in `streamMode`. Set `unstable_allowCancellation: true` to wire up the stop button. A nested conversation per sub-agent on LangGraph needs `@assistant-ui/react-langchain`, which attaches each `task` subagent's transcript to its tool call.

```ts title="runtime.ts"
import { useMemo } from "react";
import {
  unstable_createLangGraphStream,
  useLangGraphRuntime,
} from "@assistant-ui/react-langgraph";

const stream = useMemo(
  () =>
    unstable_createLangGraphStream({
      client,
      assistantId,
      // "updates" carries the subgraph events; "custom" is required for generative UI
      streamMode: ["messages", "updates", "custom"],
      // without it the run streams the top graph only
      streamSubgraphs: true,
      onDisconnect: "cancel",
    }),
  [client, assistantId],
);

const runtime = useLangGraphRuntime({
  unstable_allowCancellation: true,
  stream,
  eventHandlers: {
    onSubgraphValues: (namespace, values) => {
      // namespace = e.g. "tools:call_abc", the sub-agent's node path
      // values contains the subgraph state, including its messages array
    },
    onSubgraphUpdates: (namespace, updates) => {
      // incremental state updates from the subgraph
    },
    onSubgraphError: (namespace, error) => {
      // error scoped to the subgraph; does not mark the parent message failed
    },
    onMessageChunk: (chunk, metadata) => {
      // metadata.namespace is set when the chunk originates from a subgraph
      // use it to attribute the chunk to the correct sub-agent
    },
  },
});
```

See [LangGraph Streaming](/docs/runtimes/langgraph/streaming) for the full event handler reference.

</Tab>
<Tab value="LangChain">

With `@assistant-ui/react-langchain` there is nothing to populate. `useStream` discovers every `task` subagent on the run, and the runtime reads that subagent's own message projection and attaches it to the spawning call's `ToolCallMessagePart.messages`, keyed by the `task` tool call id. The transcript streams while the subagent runs, nests recursively up to sixteen levels deep when subagents spawn subagents, and is present again on a thread loaded from history, because the SDK seeds subagent discovery from checkpoint messages.

See [subagent and subgraph views](/docs/runtimes/langchain#subagent-and-subgraph-views) for the discovery hooks and custom views.

</Tab>
<Tab value="AG-UI">

With `@assistant-ui/react-ag-ui` there is no `messages` field to populate: the runtime builds the nesting from the protocol's own subagent lifecycle. A backend running the agents-as-tools pattern emits `SUBAGENT_STARTED` naming the spawning call as `parentToolCallId`, tags every event that subagent produces with its `subagentRunId`, and closes the run with `SUBAGENT_FINISHED` or `SUBAGENT_ERROR`. The runtime groups each run into one nested assistant message and attaches it to that call's `ToolCallMessagePart.messages`, so the tool UI above renders it unchanged.

The subagent's `name`, `description`, `result`, `interruptIds`, and `errorCode` ride on the nested message's `metadata.custom.agui`. A run whose `parentToolCallId` names no reachable call has nowhere to nest and renders in the parent thread instead.

See [AG-UI Subagents](/docs/runtimes/ag-ui/runtime-options#subagents) for the full behavior, how a suspended subagent's interrupts are answered, the comparison with LangChain's discovery-hook shape, and the one limitation (nesting does not survive a reload).

</Tab>

### Register the Toolkit

Register the toolkit like any other with `Tools({ toolkit })`; [Registering a toolkit](/docs/tools/defining-tools#registering-a-toolkit-with-tools) covers where to mount it. Because renderers are inherited, the entry also renders when the tool call sits inside another sub-agent's transcript.

```tsx
import { AssistantRuntimeProvider, AuiConfig, Tools } from "@assistant-ui/react";
import toolkit from "./sub-agent-toolkit";

const config = AuiConfig({ tools: Tools({ toolkit }) });

function App() {
  return (
    <AssistantRuntimeProvider runtime={runtime} config={config}>
      <Thread />
    </AssistantRuntimeProvider>
  );
}
```

## Recursive Sub-Agents

If a sub-agent's tool calls also have nested messages, the same pattern applies recursively. Here the planner's transcript contains `invoke_researcher` calls, rendered inline with their own nested transcript:

```tsx title="app/planner-toolkit.tsx"
"use client";

import {
  defineToolkit,
  MessagePartPrimitive,
  MessagePrimitive,
} from "@assistant-ui/react";

export default defineToolkit({
  invoke_planner: {
    type: "backend",
    render: () => (
      <div className="rounded border p-3">
        <h4>Planner agent</h4>
        <MessagePartPrimitive.Messages>
          {({ message }) => {
            if (message.role === "user") return <MyUserMessage />;
            return (
              <MessagePrimitive.Parts>
                {({ part }) => {
                  if (part.type === "text") return <MyText />;
                  if (
                    part.type === "tool-call" &&
                    part.toolName === "invoke_researcher"
                  ) {
                    return (
                      <div className="ml-4 rounded border p-3">
                        <h5>Researcher agent</h5>
                        {/* The nested transcript renders with the same primitive */}
                        <MessagePartPrimitive.Messages>
                          {({ message }) =>
                            message.role === "user" ? (
                              <MyUserMessage />
                            ) : (
                              <MyAssistantMessage />
                            )
                          }
                        </MessagePartPrimitive.Messages>
                      </div>
                    );
                  }
                  if (part.type === "tool-call") {
                    return <MyToolFallback {...part} />;
                  }
                  return null;
                }}
              </MessagePrimitive.Parts>
            );
          }}
        </MessagePartPrimitive.Messages>
      </div>
    ),
  },
});
```

## Status

While a nested conversation has a running assistant message, the tool call and the message that holds it stay `running` even after the outer run has ended. This is how delegated work that outlives the run shows up. Once the nested conversation settles without a tool result, the message reads `requires-action` with reason `tool-calls`, the same as any other pending tool call.

The nested thread rendered by `MessagePartPrimitive.Messages` or `ReadonlyThreadProvider` reports `isRunning` from its trailing assistant message, and the background rule reads the same trailing message. A runtime that fills `messages` owns settling the nested status: a trailing nested assistant message left `running` keeps the outer message `running` until it is settled. On the `useExternalMessageConverter` path a cancelled run clears it; on the plain `useExternalStoreRuntime` path the store settles the nested transcript on cancel as well. A transcript imported from persistence starts idle: a nested message that was saved while running does not keep the outer message running.

## Tasks

`s.thread.tasks` derives child work from every tool call that carries a `messages` array, including an empty array. Tasks follow document order, with nested tasks directly after their parent. Each task includes `parentTaskId` and `depth` for reconstructing the hierarchy.

The array keeps its identity while no task changes, so a component that subscribes to it does not rerender for unrelated streamed tokens. The walk stops past 32 levels of nesting; deeper tasks are not listed.

```tsx
import { useMemo } from "react";
import { useAuiState } from "@assistant-ui/react";

function TasksChip() {
  const tasks = useAuiState((s) => s.thread.tasks);
  const { running, total } = useMemo(
    () => ({
      running: tasks.filter((task) => task.status.type === "running").length,
      total: tasks.length,
    }),
    [tasks],
  );

  return <span>{`${running}/${total} tasks running`}</span>;
}
```

For imperative lookup, `aui.thread.task({ id })` resolves the first task with that toolCallId in document order (nested conversations may repeat ids), or use an index selector.

## Kit elements

[`Task card`](/elements/task-card) renders nested tool calls inside `Thread` once `components.TaskGroup` is set: every tool call that carries `messages` and has no registered tool UI becomes a lane with its state and timing, sibling tasks are grouped four at a time, and each nested transcript opens on demand.

[`Agent status`](/elements/agent-status) reads `s.thread.tasks` for a compact task summary. Its chip reports the current work, and its tray lists every task with nesting, state, label, meta, and elapsed time.

## ReadonlyThreadProvider

For advanced use cases where you have a `ThreadMessage[]` array and want to render it as a thread outside of a tool call context, use `ReadonlyThreadProvider` directly:

```tsx
import {
  ReadonlyThreadProvider,
  ThreadPrimitive,
  type ThreadMessage,
} from "@assistant-ui/react";

function SubConversation({
  messages,
}: {
  messages: readonly ThreadMessage[];
}) {
  return (
    <ReadonlyThreadProvider messages={messages}>
      <ThreadPrimitive.Messages>
        {({ message }) => {
          if (message.role === "user") return <MyUserMessage />;
          return <MyAssistantMessage />;
        }}
      </ThreadPrimitive.Messages>
    </ReadonlyThreadProvider>
  );
}
```

`ReadonlyThreadProvider` inherits the parent's tool UI registrations and model context through scope inheritance. As in a nested transcript, `s.thread.capabilities.answerToolCall` is `false` inside it, so [tool UIs show a request without its controls](/docs/tools/tool-ui#human-in-the-loop).
