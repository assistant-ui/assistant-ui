An assistant-ui app has three parts. Components draw the chat. A runtime holds the conversation and talks to your backend. Assistant Cloud, which is optional, stores the conversations and can report on runs. Read this page before you pick a runtime, so you know which part owns what.

## The parts in code

This is the chat page from [manual installation](/docs/manual-installation), which connects to an AI SDK route on your server:

```tsx title="app/page.tsx"
"use client";

import { AssistantRuntimeProvider } from "@assistant-ui/react";
import { useChatRuntime, AssistantChatTransport } from "@assistant-ui/ai-sdk";
import { Thread } from "@/components/assistant-ui/elements/thread.aui";

export default function Page() {
  const runtime = useChatRuntime({
    transport: new AssistantChatTransport({ api: "/api/chat" }),
  });

  return (
    <AssistantRuntimeProvider runtime={runtime}>
      <Thread />
    </AssistantRuntimeProvider>
  );
}
```

- `useChatRuntime` creates the runtime. It keeps the messages and sends each turn to `/api/chat`.
- `AssistantRuntimeProvider` makes the runtime available to every component inside it.
- `Thread` is a component. It renders the messages and the composer, and sends what the user does back to the runtime.
- `/api/chat` is the backend. It calls the model and streams the answer back. The components and the runtime never call the model themselves.

## Components

The components are the chat you see: `Thread`, `ThreadList`, `AssistantModal` and the rest of the [elements](/elements). The CLI copies them into your project under `components/assistant-ui`, so you can edit them like the rest of your code.

They are built from [primitives](/docs/primitives), unstyled parts such as `ThreadPrimitive.Viewport` and `ComposerPrimitive.Input`. Use the primitives directly when you want a layout the styled components don't give you.

Components never talk to your backend. They read state from the runtime and send actions to it, such as sending, editing or regenerating a message.

## Runtime

The runtime manages the conversation: the messages, the composer, the run in progress, branches, edits and regenerations. With most runtimes you never handle the messages yourself. `useExternalStoreRuntime` instead reads them from a store you own and calls your handlers when the user sends, edits or reloads a message. The runtime also converts the messages your backend sends into the message parts the components render.

Each chat uses one runtime, chosen by its backend:

- `useChatRuntime` from `@assistant-ui/ai-sdk` for the Vercel AI SDK.
- `useLangGraphRuntime` from `@assistant-ui/react-langgraph` for LangGraph, with similar adapters for LangChain, Google ADK, A2A, AG-UI and others.
- `useLocalRuntime` when you write the call to your backend yourself.
- `useExternalStoreRuntime` when your app already keeps the messages in its own store, such as Redux or Zustand.

[Pick a runtime](/docs/runtimes/pick-a-runtime) compares them, and [runtime architecture](/docs/runtimes/concepts/architecture) shows how they build on each other.

## Backend

Your backend produces the answers. It can be a route that calls a model through the AI SDK, an agent framework such as LangGraph or Mastra, or any server whose output a runtime can read. It streams text, tool calls, reasoning and agent state, and the runtime turns each into parts of a message.

When no runtime fits your backend, have it send the [data stream](/docs/runtimes/custom/data-stream) or [assistant transport](/docs/runtimes/custom/assistant-transport) protocol, and use the runtime made for it.

## Assistant Cloud

[Assistant Cloud](/docs/cloud) is a hosted service the runtime writes to. It stores threads and messages, so a user can return to a conversation later or on another device. It can also record run reports and the actions users take, and shows them in a dashboard. What it stores and reports depends on the runtime; [which runtime](/docs/cloud/runtimes) lists each one.

Cloud is optional. You can store threads in your own database through a thread list adapter instead. [Threads](/docs/runtimes/concepts/threads) covers both.

### The browser calls an agent server

The runtime connects straight to a service that accepts requests from the browser, such as an [A2A](/docs/runtimes/a2a/overview) or [AG-UI](/docs/runtimes/ag-ui/overview) agent server. Never put a model provider's API key in the browser, because every user can read it.

### Your server calls the model

A route on your server sits between the runtime and the model, as in the example above. API keys, server-side tools and authorization stay on your server. This is the most common setup.

Your server still produces the answers. The runtime also writes the conversation to the cloud, and your server can send its traces and scores there. The cloud calls models through the [LLM providers](/docs/cloud/llm-providers) you connect, for features such as thread titles.
