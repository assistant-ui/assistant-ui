## API Reference

### unstable_Interactables

<Callout type="tip">
<strong>Experimental.</strong> Shipped 2026-06-23; it may change in any release.
</Callout>

Registers the interactables store scope, which holds the state of every
mounted interactable and exposes it to the model.

Mount it as `unstable_interactables` in an `AuiConfig`. For each interactable
name with a registered instance it adds one `update_{name}` frontend tool to
the `modelContext` scope, and it stamps the state of changed instances onto
each outgoing user message as `metadata.custom.interactables`. Your route
has to upload the model context's tools and turn those snapshots into text
(`unstable_injectInteractableContext` in `@assistant-ui/ai-sdk`).

Pass a `persistence` adapter to keep app-scoped state across reloads.
Thread-scoped instances never use the adapter; they restore from the
thread's history. Keep the adapter object stable, because a new adapter
identity starts a new persistence scope and resets app-scoped state.

```tsx
const config = AuiConfig({
  unstable_interactables: unstable_Interactables({ persistence: adapter }),
});
```

```ts
const unstable_Interactables: Resource<ClientOutput<"unstable_interactables">, [(Unstable_InteractablesConfig | undefined)?]>;
```

### unstable_useInteractable

<Callout type="tip">
<strong>Experimental.</strong> Shipped 2026-06-23; it may change in any release.
</Callout>

Registers an interactable with the AI assistant and returns its live state,
like `useState` that the model can also read and update.

Call this once per place that shows the interactable. Other components can
read and write the same instance by passing its `id` to
`unstable_useInteractableState`.

For tool-created interactables rendered inside tool-call message parts,
`version` carries this message's version of the instance — its state as of
that point in the conversation, whether it is the most recent tool-driven
version, and a `restore()` back to it. Whether older messages render frozen history or stay
live-editable is the component's choice. Inside an `update_{name}` part the
instance `id` is inferred from the call, so the same component works at the
creating call and at update calls.

### unstable_useInteractableVersions

<Callout type="tip">
<strong>Experimental.</strong> Shipped 2026-06-23; it may change in any release.
</Callout>

Every version of a tool-created interactable recorded in the current
thread, oldest first: the creating tool call, each user edit, and each
`update_*` call. Each entry carries the full state as of that version and a
`restore()` that sets the live instance back to it — enough for a version
picker like an artifact's history dropdown.

### unstable_interactableTool

<Callout type="tip">
<strong>Experimental.</strong> Shipped 2026-06-23; it may change in any release.
</Callout>

Defines a tool that creates a thread-scoped interactable from its arguments,
for assignment to a toolkit entry — the entry key is the creating tool's
name, and the interactable's unless `name` gives it another:

```tsx
notepad: unstable_interactableTool({
  description: "A notepad the user can read and edit.",
  stateSchema: notepadSchema,
  render: (props) => <Notepad {...props} />,
}),
```

`render` shows at the creating call and — installed automatically — at every
`update_{name}` call, with streaming previews, instance-id wiring, and
registration handled. It receives the live `state`/`setState` plus this
message's `version`; whether older messages render frozen history or stay
live-editable is the render function's choice.

The entry is a frontend tool whose arguments are the interactable's initial
state, and its instance id is the creating call's `toolCallId`. The
interactables scope (`unstable_Interactables`) must be mounted, because it
owns the `update_{name}` tool. In a `"use generative"` file, pass an inline
object literal and import this function from an assistant-ui package, or the
compiler rejects the entry.

```ts
const unstable_interactableTool: <TSchema extends Unstable_InteractableStateSchema>(config: Unstable_InteractableToolConfig<TSchema>) => ToolDefinition<Record<string, unknown>, { success: true; interactable?: string | undefined; }>;
```

### unstable_getInteractableVersions

<Callout type="tip">
<strong>Experimental.</strong> Shipped 2026-06-23; it may change in any release.
</Callout>

Every version of interactable `id` recorded in the thread, oldest first,
folded chronologically:

- the tool call whose `toolCallId` equals `id` seeds the baseline with its
  args (`origin: "create"`) — the `id: toolCallId` convention for
  tool-created interactables,
- a snapshot stamped on a user message is a `"user-edit"` version (a full
  snapshot replaces the state; a partial one shallow-merges),
- each accepted `update_*` call shallow-merges an `"update"` version.

The last entry is the state the model knows. Partial snapshots and update
calls with no baseline to merge into are skipped.
