title: With assistant-ui
description: Render widget tool calls in an assistant-ui thread as their arguments stream, and report render errors back to the model.

`generative-frame/assistant-ui` turns the widget tools into an assistant-ui toolkit. It needs `@assistant-ui/react`, an optional peer that only this entry imports.

## Set up the toolkit

```tsx
"use client";

import type { ReactNode } from "react";
import { AssistantRuntimeProvider, AuiConfig, Tools } from "@assistant-ui/react";
import { useChatRuntime } from "@assistant-ui/ai-sdk";
import { lastAssistantMessageIsCompleteWithToolCalls } from "ai";
import {
  createWidgetToolkit,
  useWidgetInstructions,
} from "generative-frame/assistant-ui";

const widgets = createWidgetToolkit({ widget: { maxHeight: 700 } });
const config = AuiConfig({ tools: Tools({ toolkit: widgets.toolkit }) });

export function Provider({ children }: { children: ReactNode }) {
  const runtime = useChatRuntime({
    sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithToolCalls,
  });
  return (
    <AssistantRuntimeProvider runtime={runtime} config={config}>
      <WidgetInstructions />
      {children}
    </AssistantRuntimeProvider>
  );
}

function WidgetInstructions() {
  useWidgetInstructions(widgets.tools);
  return null;
}
```

`createWidgetToolkit` returns `{ toolkit, tools, registry }`. `toolkit` holds entries for `read_me`, `show_widget`, `edit_widget`, `preview_widget`, and, when you pass `spec`, `render_spec`. `tools` are the underlying [tool definitions](/generative-frame/docs/tools), and `registry` holds the latest code per widget title.

`useWidgetInstructions(tools, { preload })` adds a short system prompt section that tells the model when to use the tools. Pass `preload: { modules: ["chart"] }` to inline the `read_me` guidance for those modules, which saves the model a round trip at the cost of a longer prompt.

## What renders in the thread

- `show_widget` streams `widget_code` from the partial tool arguments into a [`<Widget>`](/generative-frame/docs/react). While no code has arrived, the first of `loading_messages` is shown as a status line.
- `edit_widget` replays the edits against the widget's code from earlier calls in the thread and renders the result.
- `render_spec` streams patches into a [`<SpecRenderer>`](/generative-frame/docs/spec-mode) with your components. It is added by the `spec` option, described next.
- `read_me` and `preview_widget` render nothing.

A widget's `sendPrompt(text)` appends a user message to the thread. Pass `widget: { onPrompt }` to handle it yourself. Everything else under `widget` (`csp`, `product`, `maxHeight`, handlers) applies to every frame the toolkit renders.

## Spec mode

The toolkit does not import the spec code. To render your own components, build spec mode with `createSpecToolkit` from `generative-frame/spec/assistant-ui` and pass it as `spec`:

```tsx
import { createWidgetToolkit } from "generative-frame/assistant-ui";
import { createSpecToolkit } from "generative-frame/spec/assistant-ui";

const widgets = createWidgetToolkit({
  spec: createSpecToolkit(catalog, { components, handlers }),
});
```

This adds `render_spec` to the toolkit and the `spec` module to `read_me`. `createSpecToolkit(catalog, options)` takes `components` (required), `handlers`, `onAction`, `placeholder`, and `specPrompt`. See [Spec mode](/generative-frame/docs/spec-mode) for the catalog and components.

The built-in `copyText` action (`{ text }`) writes `text` to the user's clipboard with `navigator.clipboard.writeText`, so a spec can offer a button such as "Copy list". It runs only from a user's event, never from `watch`, and the `spec` module documents it for the model.

Results of the tool calls before a `render_spec` call are in its state under `/tools/<toolName>/<n>`, newest first, so a spec can show a value such as a price straight from the latest search with `{ "$state": "/tools/search_flights/0/price" }` instead of the model copying it. Tool names are keys every model sees, which call ids are not, and counting back from the call keeps each index stable when the host prunes older history, as AI SDK `pruneMessages` and LangChain `trimMessages` do. A patch counts from its own call, so the `spec` module tells the model where the results are and to update a binding that should keep an older result after calling the same tool again. The widget tools' own results are left out, a call without a result yet holds `undefined`, and a spec that writes its own `tools` key in `state` keeps it and gets no results, so specs saved before this release render as they did. A string result that holds a JSON object or array, such as a LangGraph tool message, is mounted decoded, because that is the structure the model read. An entry is the result the thread stores, so an AI SDK tool with `toModelOutput` exposes its `execute` result rather than the output the model saw. This needs frontend execution, where the toolkit's own `read_me` tells the model about `tools`; with `execution: "backend"` the server's `read_me` does not carry that rule, so the toolkit leaves `state` as the model wrote it.

### On React Native

`createWidgetToolkit` and frame mode run only in a browser. With `@assistant-ui/react-native`, `createSpecToolkit` from `generative-frame/spec/assistant-ui` resolves to a React Native build, and its entries go straight into your toolkit:

```tsx
import { Tools, useAssistantInstructions } from "@assistant-ui/react-native";
import { createSpecToolkit } from "generative-frame/spec/assistant-ui";

const spec = createSpecToolkit(catalog, { components });
const tools = Tools({
  toolkit: spec.entries({ execution: "frontend", display: "standalone" }),
});
const guidance = (spec.modules ?? [])
  .map((module) => module.guidance())
  .join("\n\n");

function SpecInstructions() {
  useAssistantInstructions(guidance);
  return null;
}
```

Pass `tools` to your `AuiConfig`, and render `SpecInstructions` inside the runtime provider so the model gets the toolkit's `spec` module, the guidance `read_me` gives it on the web, including your `specPrompt` and the rule for earlier tool results. With `execution: "backend"`, the server defines `render_spec` with `createSpecTools(catalog)` and puts the catalog guidance in its system prompt instead, as in [spec mode as a tool](/generative-frame/docs/spec-mode#as-a-tool); earlier tool results reach a spec's state only in frontend execution, so that guidance leaves out their rule. What the user changes in a rendered spec is saved and restored as on the web (see [History after a reload](#history-after-a-reload)). React Native has no clipboard API of its own, so this build leaves `copyText` out of the guidance; an app that has a clipboard module adds it with `handlers: { copyText }` and `specPrompt: { hostApi: { clipboard: true } }`. `@assistant-ui/react-native` is an optional peer of this entry.

## Frontend and backend execution

By default the tools execute in the browser. Your route forwards their schemas to the model with `frontendTools` from `@assistant-ui/ai-sdk`:

```ts title="app/api/chat/route.ts (abridged)"
import { frontendTools } from "@assistant-ui/ai-sdk";
import { convertToModelMessages, streamText, type UIMessage } from "ai";

export async function POST(req: Request) {
  const { messages, system, tools } = (await req.json()) as {
    messages: UIMessage[];
    system?: string;
    tools?: Parameters<typeof frontendTools>[0];
  };
  const result = streamText({
    model,
    messages: await convertToModelMessages(messages),
    ...(system ? { system } : {}),
    tools: frontendTools(tools ?? {}),
  });
  // return the UI message stream response as your route already does
}
```

The instructions from `useWidgetInstructions` arrive in `system`.

With `execution: "backend"`, the toolkit only renders, and the server runs the tools:

```ts
import { jsonSchema, streamText } from "ai";
import {
  buildWidgetInstructions,
  createWidgetTools,
  toAISDKTools,
} from "generative-frame/tools";

const widgetTools = createWidgetTools();
const { preview_widget: _preview, ...serverTools } = widgetTools;

const result = streamText({
  model,
  system: await buildWidgetInstructions(widgetTools),
  messages,
  tools: toAISDKTools(serverTools, { jsonSchema }),
});
```

`preview_widget` is left out here because previews need a browser. The server's registry lives in that process, so create one per conversation; `createWidgetRegistry(initial)` from `generative-frame/tools` seeds it with existing widgets. Live render reports, described next, are only available in frontend execution. With spec mode, the server adds `render_spec` the same way, through `extraTools` and `modules` (see [Spec mode](/generative-frame/docs/spec-mode#as-a-tool)).

## Render errors reach the model

In frontend execution, the `show_widget` and `edit_widget` results wait for the frame in the thread to finish rendering and carry a `render` field:

```ts
// the frame ended and settled
{ status: "rendered", ok, blank, height, errors, console, feedback }

// the frame had not finished within the timeout
{ status: "timeout", feedback }
```

`errors` are the widget's errors, `console` its console warnings and errors (most recent last), and `feedback` is model-readable text in the same format as [`buildRepairFeedback`](/generative-frame/docs/repair). The model sees a script error, a blocked resource, or a blank render in the tool result and can fix it with `edit_widget`. A call that fails before rendering (an empty `widget_code`, an edit that does not match) returns its error without `render`.

```ts
createWidgetToolkit({ renderReport: { timeoutMs: 15000, settleMs: 500 } });
```

`timeoutMs` (default 10000 ms) caps how long a result waits. `settleMs` (default 300 ms) is the wait after the code ends, so errors from scripts that run a little later are caught. `renderReport: false` returns each result as soon as the code is stored.

## `preview_widget`

The toolkit includes `preview_widget`, executed in the browser with `previewWidget` from the core entry. Pass `preview` to use a different renderer. The result is the [preview result](/generative-frame/docs/repair#previewwidget) plus `feedback` text, without the PNG screenshot, because a base64 image in a JSON tool result is large. Set `previewScreenshot: true` to keep it.

## Theme

Frames follow the app's shadcn/ui theme through `useAssistantUiThemeTokens`, which reads shadcn variables first (`--background`, `--primary`, `--muted`, and so on). Pass `themeElement` to read from an element other than the document root. The hook is exported for your own `<Widget>`s:

```tsx
import { useAssistantUiThemeTokens } from "generative-frame/assistant-ui";

const tokens = useAssistantUiThemeTokens();
```

## History after a reload

The renderers derive their state from the thread, not from memory. `show_widget` renders from its arguments, `edit_widget` replays the edits of earlier calls with the same title, and `render_spec` applies its patches onto the spec built by earlier calls with that title. The registry is filled from rendered calls, so `edit_widget` also executes after a reload. Scripts run again when a widget mounts.

What the user changes in a rendered spec, through a bound input, a `setState` action, or a value a handler writes, is saved on its `render_spec` call with `unstable_recordInteraction` half a second after the last change and when the call unmounts, and restored when the call renders again. It comes back after a reload with any runtime that keeps tool interactions with the thread (see [Recording interactions](/docs/tools/tool-ui#recording-interactions)), and it is not sent to the model unless the UI shares it, as described below. Each call keeps its own changes, so a later `render_spec` call with the same title starts from the spec the model wrote. Saving is best effort: the state has to be plain JSON within the runtime's 16,384-character limit for one interaction, and a save that fails is recorded as such, so the call starts from the model's state after a reload rather than from an older save. A change made in the last half second before the call unmounts, for example when switching threads, may not be saved.

A UI tells the model what the user chose only on purpose. In a spec, the built-in `updateModelContext` action (`{ text?, data? }`) replaces what the UI shares, and `sendMessage` (`{ text }`) sends a user message; a widget calls `genframe.updateModelContext({ content: [{ type: "text", text }], structuredContent })` or `sendPrompt(text)`. The toolkit adds what each UI shares to the system prompt of every later request, including one that `sendMessage` starts in the same event, as a section that names the UI, marks the shared value as data rather than instructions, and holds at most 4,000 characters of it. It saves the context with the call's state, so it comes back after a reload wherever the state does, on the same best effort terms, and drops it when the UI shares empty params. `sendMessage` runs only from a user's event, never from `watch`. Your own `handlers` in `createSpecToolkit`, or `widget.onUpdateModelContext` in `createWidgetToolkit`, replace these defaults.

A widget's own state, the value its script passes to `genframe.setState`, is saved the same way on the `show_widget` or `edit_widget` call that drew it, and `genframe.state` holds the saved value when the widget's scripts run again after a reload. Each call keeps its own state, so an `edit_widget` call starts from the state its own frame saved, or `null`, and the same plain JSON limit applies. Your `onWidgetState` handler still receives every state the host accepts: plain JSON from the frame that is showing.

## Storage

Each widget's frame gets a [storage id](/generative-frame/docs/quickstart#persistent-storage) made of the thread's persisted id and the `toolCallId` of the `show_widget` call that created it: `<remoteId>:<toolCallId>`. Its localStorage survives a reload and carries over to its `edit_widget` versions. Both parts come from the runtime and the provider, not from arguments the model writes.

A thread gets its `remoteId` when a thread list adapter (for example Assistant Cloud) persists it. Without one, or before it is persisted, the id is `aui:<toolCallId>`. The id is read when a frame mounts and never changes while it is mounted, so a widget drawn before its new thread was persisted keeps its storage for that page view, and starts with empty storage after a reload, when the thread's remote id is known.

Pass `widgetId: ({ toolCallId, threadId }) => …` to choose ids yourself, or `widgetId: false` to give every frame a fresh origin.
