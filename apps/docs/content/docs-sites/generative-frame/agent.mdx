---
title: Agent delegation
description: Move widget generation into a sub-agent behind one generate_widget tool, with a provider-neutral model interface.
---

By default the main agent calls `show_widget` itself. `generative-frame/agent` moves that work into a sub-agent: the main agent gets one tool, `generate_widget`, and the sub-agent reads the guidance, writes the widget, checks the render, and repairs it.

## Create the agent

```ts
import { createWidget } from "generative-frame";
import { createWidgetAgent, fromAISDK } from "generative-frame/agent";
import { jsonSchema, streamText } from "ai";

const agent = createWidgetAgent({
  model: fromAISDK({ streamText, jsonSchema, model: widgetModel }),
  createSink: () => createWidget({ container: nextWidgetSlot() }),
  maxRounds: 3,
});
```

Give `agent.tool` to the main agent like any other [tool definition](/generative-frame/docs/tools):

```ts
import { toAISDKTools } from "generative-frame/tools";

const tools = toAISDKTools({ generate_widget: agent.tool }, { jsonSchema });
```

`generate_widget` takes `{ brief, data?, mode?, title? }`. `brief` describes the widget in plain language, `data` is passed through as JSON, and `mode` is `"html"` (the default) or `"spec"`. The result is short:

```ts
{ ok, title, mode, summary, errors, code?, spec?, rounds }
```

`summary` is the sub-agent's one sentence about what it built, and `errors` lists problems left in the final render.

You can also call `agent.generate(input, { signal, sink, onEvent })` directly.

## What the sub-agent does

1. Calls `read_me` with the modules it needs.
2. Calls `show_widget` (or `render_spec` in spec mode). Tool-call arguments stream into the sink as the model writes them.
3. Checks the render: with `preview` it renders the code offscreen, otherwise it waits `settleMs` and calls the sink's `inspect()`.
4. Feeds the result back as the tool result and repairs with `edit_widget` or more patches, up to `maxRounds` renders.
5. Replies with one sentence, which becomes `summary`.

Only the first `show_widget` streams. A later full re-send replaces the widget once it is complete, because a frame cannot restart a stream after its scripts ran.

For spec mode, pass tools created with a catalog:

```ts
const agent = createWidgetAgent({
  model,
  tools: createWidgetTools({ catalog }),
});

await agent.generate(
  { brief: "Order summary with a reload button", mode: "spec" },
  { sink: { spec: (spec, { streaming }) => renderSpec(spec, streaming) } },
);
```

## Sinks

A sink receives the widget as it is generated. Every member is optional:

```ts
type WidgetSink = {
  write?(chunk: string): void;
  end?(): Promise<unknown>;
  replace?(code: string): Promise<unknown>;
  inspect?(): Promise<Pick<WidgetInspection, "errors" | "console" | "blank" | "size">>;
  spec?(spec: Spec, info: { streaming: boolean }): void;
};
```

A `WidgetHandle` from `createWidget` satisfies the HTML members. Pass a sink per call with `generate(input, { sink })`, or `createSink({ title, mode })` for calls that arrive through the tool.

## The model interface

The model is any function that streams one assistant response:

```ts
type WidgetAgentModel = (
  messages: readonly AgentMessage[],
  options: { tools: readonly AgentToolDeclaration[]; signal?: AbortSignal },
) => AsyncIterable<AgentModelEvent>;
```

It yields these events:

| Event | Meaning |
| --- | --- |
| `{ type: "text-delta", text }` | Assistant text. |
| `{ type: "tool-call-delta", id, name?, argsTextDelta }` | A piece of a tool call's JSON arguments. `name` is required on the first delta of a call. |
| `{ type: "tool-call", id, name, args }` | A tool call with complete arguments. Every call ends with one, whether or not it streamed deltas. |
| `{ type: "finish", reason? }` | The response is complete. |

The agent runs the tools itself, so the model function must not execute them. `fromAISDK({ streamText, jsonSchema, model, settings })` adapts the AI SDK without making `ai` a dependency; `settings` is spread into `streamText`.

## Inline or delegated

Inline generation is the fastest path: one model writes the widget while it talks, but every widget's guidance and code lands in the main agent's context.

Delegation keeps the main context small and lets a cheaper or specialized model draw. It adds at least one extra model call of latency, and the main agent knows the widget only through its brief and the returned summary.
